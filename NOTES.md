СТОИМОСТЬ НЕ ХРАНИТСЯ, А СЧИТАЕТСЯ ПРИ ЧТЕНИИ

Поэтому в time_entries лежат только часы, а ставка и стоимость считаются в агрегации.


АРХИТЕКТУРА ЧИСТАЯ

    Api -> Application -> Domain
                  ^
           Infrastructure

1. Domain - сущности и правила, ноль внешних зависимостей. Маппинг на BSON вынесен
   в MongoMappings, поэтому правила тестируются без базы и моков.
2. Application - команды и запросы MediatR, валидаторы FluentValidation, интерфейсы репозиториев.
3. Infrastructure - MongoDB: репозитории на запись и отдельная читающая сторона
   (ITimeEntryReader, IProjectReportReader), возвращающая сразу модель экрана.
4. Api - тонкие контроллеры, вся работа это _mediator.Send(...).


Валидация входных данных (FluentValidation в пайплайне MediatR) отделена от бизнес-правил
(домен).


ИНДЕКСЫ

Создаются в MongoIndexInitializer при старте API.
Имена заданы вручную, чтобы в explain() было видно, какой индекс сработал.

1. time_entries { date: 1, projectId: 1 } - ix_date_project
   Отчёт за месяц и список табеля. date первым, потому что диапазон по месяцу есть в каждом
   запросе к коллекции, а projectId - не в каждом.

2. time_entries { employeeId: 1, date: 1 } - ix_employee_date
   Проверка лимита 24 часа при каждом создании и изменении записи, фильтр
   по сотруднику, дневные итоги для флага переработки.

3. time_entries { projectId: 1, date: 1 } - ix_project_date
   Фильтр по проекту, когда сотрудник не выбран.

4. projects { code: 1 } unique - ux_code
   Уникальность шифра из ТЗ.

5. employees { fullName: 1 } - ix_full_name
   Сортировка справочника.

6. closed_periods { year: 1, month: 1 } unique - ux_year_month
   Проверка "закрыт ли период" на каждой операции с табелем. Уникальность защищает от двойного
   закрытия при гонке: DuplicateKey превращается в 409.

Цена записи: три индекса на time_entries - каждая вставка обновляет четыре структуры. Для
табеля размен правильный, записей создают единицы в день, а читают постоянно.



КОДЫ ОШИБОК

400 - с запросом что-то не так. 409 - запрос корректен, но конфликтует с состоянием системы.
Клиент по статусу отличает "поправь поле" от "обнови страницу".

    VALIDATION_ERROR            400   часы не кратны 0,5, не выбран сотрудник, сломанный JSON
    EMPLOYEE_RATE_NOT_FOUND     400   на дату записи у сотрудника ещё нет ставки
    DATE_OUT_OF_PROJECT_PERIOD  400   дата вне периода проекта
    DAILY_HOURS_LIMIT_EXCEEDED  409   суммарно за день больше 24 часов
    PERIOD_CLOSED               409   месяц закрыт бухгалтерией
    CONCURRENCY_CONFLICT        409   запись изменили после того, как её открыли
    PERIOD_ALREADY_CLOSED       409   повторное закрытие месяца
    NOT_FOUND                   404   нет записи, сотрудника или проекта
    INTERNAL_ERROR              500   всё остальное, с логом и без деталей наружу



КОНКУРЕНТНОЕ РЕДАКТИРОВАНИЕ

У записи табеля есть version. Обновление идёт одним запросом с условием на версию.
MatchedCount = 0 означает, что кто-то успел раньше - 409 CONCURRENCY_CONFLICT.


ФРОНТЕНД

Состояние - TanStack Query. Всё, что показывают экраны, это серверное состояние, ему нужен кэш
с инвалидацией после мутаций, а не собственное хранилище: redux или mobx означали бы ручную
синхронизацию копии серверных данных, то есть второй источник правды. Фильтры и открытая
модалка - обычный useState.

Формы без библиотеки. Ошибки раскладываются по полям
через errors[].field. Поле часов сделано с step="0.1", чтобы браузер не мешал ввести 3,7
и пользователь увидел наше сообщение.
